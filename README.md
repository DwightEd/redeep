# ReDeEP token-AUROC reproduction

This repository reproduces
[**ReDeEP: Detecting Hallucination in Retrieval-Augmented Generation via
Mechanistic Interpretability**](https://arxiv.org/abs/2410.11414) on the
official [RAGTruth](https://github.com/ParticleMedia/RAGTruth) responses
generated by `llama-2-7b-chat`.  The
[original ReDeEP code](https://github.com/Jeryi-Sun/ReDEeP-ICLR) is retained
as the reference implementation (audited at commit
`4d081915b8fb4430fda65c411da61540cc73cc57`). This repository teacher-forces
those fixed responses through two scoring backbones:

- `Meta-Llama-3.1-8B-Instruct`
- `Qwen3-8B`

This is a **cross-backbone ReDeEP rescoring experiment**.  It is intentionally
not described as the paper's same-generator/same-detector setting: the text
and human hallucination spans come from Llama2, while ECS/PKS internal states
come from the target scorer.

The primary result is literal pooled-token AUROC for each of QA, Data2txt, and
Summary.  A secondary paper-compatible result averages token scores within a
response before computing response-level AUROC.

The complete frozen protocol is in
[`docs/EXPERIMENT_PROTOCOL.md`](docs/EXPERIMENT_PROTOCOL.md).

## Remote setup

```bash
git clone https://github.com/DwightEd/redeep.git
cd redeep
bash scripts/setup_remote.sh
source .venv/bin/activate
redeep --config configs/experiment.yaml doctor
```

If the cluster requires a CUDA-specific PyTorch wheel, create/activate the
environment and install that wheel first, then run:

```bash
python -m pip install -e ".[dev]"
```

`doctor` verifies file mounts, fast tokenizers, model architecture metadata,
the pinned Transformers version, CUDA/BF16 support, and hashes. `audit-data`
performs the full source/response join, exact span/context checks, official
counts, and deterministic dev split:

```bash
redeep --config configs/experiment.yaml audit-data
```

## Run

Run one scorer:

```bash
bash scripts/run_model.sh llama31
bash scripts/run_model.sh qwen3
```

Or run both sequentially:

```bash
bash scripts/run_all.sh
```

The pipeline is also exposed stage by stage:

```bash
redeep --config configs/experiment.yaml discover-heads --model llama31
redeep --config configs/experiment.yaml extract --model llama31 --split calibration_train
redeep --config configs/experiment.yaml extract --model llama31 --split dev
redeep --config configs/experiment.yaml extract --model llama31 --split test
redeep --config configs/experiment.yaml calibrate --model llama31
redeep --config configs/experiment.yaml evaluate --model llama31
redeep --config configs/experiment.yaml compare --first llama31 --second qwen3
```

For a smoke extraction, add `--limit 1`.  Do not calibrate/evaluate a limited
run.  Each response is an atomic Parquet shard; rerunning `extract` skips
completed shards.  `--force` deliberately recomputes the selected stage.
Run this one-response smoke before launching all three full splits and record
its wall time plus peak GPU/CPU memory.

### Resume artifacts created before the alignment fix

Older commits rendered the fixed response through the model chat template.
Llama's Jinja template trims message content, so RAGTruth response `17235`,
whose raw text ends in a newline, failed exact character alignment. Current
code appends the response verbatim.

Because feature manifests pin the code commit, pull the fix and explicitly
adopt compatible completed shards before resuming. The adoption command first
verifies the old commit plus the config, data, model, tokenizer, Copying Heads,
and every Parquet hash. It records the old provenance, backs up the original
manifests, and never changes Parquet values.

```bash
git pull --ff-only
source .venv/bin/activate

python scripts/adopt_alignment_resume.py \
  --config configs/experiment.yaml --model llama31

python scripts/adopt_alignment_resume.py \
  --config configs/experiment.yaml --model llama31 --apply

CUDA_VISIBLE_DEVICES=0 bash scripts/run_model.sh llama31
```

Do not add `--force`; the resumed run skips the adopted shards and starts from
the first missing response.

Mechanistic extraction directly reads projection weights, so Accelerate
CPU/disk offload is rejected. With `device_map: auto`, expose enough GPU
memory (one or multiple GPUs) to keep the complete 8B model resident.
At the first stage in each CLI process, checkpoint shards are SHA256-hashed;
this adds a short storage-bound startup pass and prevents resume from silently
mixing features produced by different weights.

Multiple GPU jobs can safely divide a split with deterministic, disjoint
response assignments.  For example, launch four workers (one command per
allocated GPU/job):

```bash
redeep --config configs/experiment.yaml extract --model llama31 \
  --split calibration_train --num-shards 4 --shard-index 0
redeep --config configs/experiment.yaml extract --model llama31 \
  --split calibration_train --num-shards 4 --shard-index 1
# Repeat for shard-index 2 and 3, then for dev and test.
```

The assignment is the fixed selected order sliced as `selected[I::N]`.
Run `calibrate` only after all workers and all three splits have completed.

GPU selection remains under the scheduler/user's control:

```bash
CUDA_VISIBLE_DEVICES=0 bash scripts/run_model.sh llama31
```

## Output layout

For the default config:

```text
outputs/
`-- redeep-ragtruth-llama2-cross-backbone/
    |-- llama31/
    |   |-- copy_heads.json
    |   |-- features/
    |   |   |-- calibration_train/*.parquet
    |   |   |-- dev/*.parquet
    |   |   `-- test/*.parquet
    |   |-- calibration.json
    |   |-- calibration_standard.json
    |   |-- calibration_legacy_redeep.json
    |   `-- results/
    |       |-- results.json
    |       |-- results.csv
    |       `-- report.md
    |-- qwen3/
    |   `-- ...
    `-- comparisons/
        `-- llama31_vs_qwen3/
```

Feature shards include the common identity/label columns
`response_id`, `task`, `quality`, `original_split`, `eval_split`, `token_index`,
`token_id`,
`token_position`, `predictor_position`, `char_start`, `char_end`, and
`token_label`, followed by per-head ECS and per-layer PKS columns.

The final report contains, for both models:

- task-wise and overall token micro-AUROC with response-cluster bootstrap CI;
- task-macro token AUROC;
- paper-compatible response AUROC;
- the `quality == good` sensitivity result;
- paired response-cluster bootstrap differences when both models are run together;
- selected Copying Heads, Knowledge FFNs, beta, hashes, and environment
  provenance.

## Reproducibility choices

- Train is deterministically partitioned into 2,365 calibration-fit and 150
  dev responses (50 per task, seed 2024).
- Test is untouched until heads/layers/beta and MinMax extrema are frozen.
- Primary PKS uses standard Jensen-Shannon divergence; the public code's
  reverse-KL/scaled calculation is separately calibrated and reported as
  `legacy_redeep`.
- Primary ECS searches retrieved-context keys only; whole-prefix ECS is a
  compatibility diagnostic.
- Copying Heads are reconstructed deterministically because the official
  repository did not release its discovery script.
- The tested runtime is Python 3.10, PyTorch 2.5.1, and
  Transformers 4.52.2. The complete core Python stack is pinned in
  `pyproject.toml`.
- Attention execution is fixed to PyTorch SDPA. ECS selects
  `max(1, floor(0.1 * valid_context_tokens))`, matching the public code's
  top-10% rounding while avoiding an empty selection.
- Copy-head, token-feature, calibration, and result artifacts carry chained
  hashes over source code, canonicalized data, full checkpoint shards,
  tokenizer files, and their upstream artifacts.
